## 2. 我們的預算拆解（§13.7 每棟每 tick 的操作成本）

| 操作 | 頻率 | 單次預算（初版可調） | 說明 |
|---|---|---:|---|
| 狀態機解析 | 每棟每 1 秒 | ≤50 ns | 純分支＋列舉比較 |
| 燃料消耗＋扣貨 | 每棟每 1 秒（多半不扣貨） | ≤200 ns | 餘量累加；只有滿 1 件才呼叫庫存 |
| 水消耗＋扣貨 | 每棟每 1 秒 | ≤200 ns | 同上 |
| 磨損與條件更新 | 每棟每 1 秒 | ≤50 ns | 一次乘加＋clamp |
| 輸出寫回節點（A 案） | 每棟每 1 秒 | ≤100 ns | B 案（占空比）無此成本 |
| 維護狀態評估 | 每棟每 1 秒 | ≤100 ns | 只在 `condition ≤ 50` 才做材料／道路查詢 |
| 狀態變化事件 | 狀態變化時 | 每棟 ≤1 次／變化 | 事件驅動 UI 更新 |
| **合計** | — | **≤3 µs／棟／tick** | 1,000 棟 → p95 ≤3 ms／1 秒 |

- 上表的操作預算加總約 700 ns，整體門檻保留到 3 µs，是刻意留給 Unity 呼叫、快取未命中、
  清單走訪與量測抖動的餘裕。
- 材料／道路可達查詢是唯一可能「非 O(1)」的操作：只在 `condition ≤ 50` 時執行，並以
  「每 10 秒最多查一次」節流；1,000 棟同時缺料也不會每 tick 掃路網。
- Tick 內禁止 `LINQ`、字串插值、會產生 GC 配置的 `foreach`；改索引迴圈與預先配置清單。
- 時間換算：**1 遊戲小時 = 19.2 真實秒**；1 遊戲日 = 460.8 秒；30 遊戲日 = 720 遊戲小時 ≈ 3.84 實時小時。
  磨損與消耗的「每小時」值換算成「每秒」一律 ÷19.2，並以遊戲時間為準（暫停不推進、加速按比例）。

## 4. p95 ≤3 ms／p99 ≤6 ms 的推導與假設

### 4.1 推導

```text
單棟預算               = 3 µs/棟/tick（§13.7 合計）
1,000 棟 p95 預算      = 3 µs × 1,000 = 3.0 ms
p99 預算              = 2 × p95 = 6.0 ms（吸收排程／GC／快取尖峰）
每秒牆鐘佔用（p95）    = 3 ms ÷ 1,000 ms = 0.3%（§12.6）
30 日（20× 速）       = 720 遊戲小時；「1,000 棟全部同時滿載」是壓力上界，不是常態負載
                        （實務單一存檔的引擎數通常數十棟，受燃料鏈與水鏈限制，§14.7）
```

> 這組數字是「1,000 棟全部同時滿載」的**壓力上界**；P8 的 p95/p99 量測必須在 30 秒取樣中
> 同時回報這兩個百分位，並以實際引擎數與 tick 視窗說明負載比例。

### 4.2 離線量測對照

- 本次代理量測：1,000 棟 p95 = **108.20 µs**（3,000 µs 的 3.6%）、p99 = **167.80 µs**（6,000 µs 的 2.8%）。
- 平均 0.053 µs/棟，是 3 µs/棟預算的 **1.8%**。
- 即「Core 純運算」只吃掉約 1/28 的 p95 預算，其餘 ~2,890 µs 留給 Unity 引擎端
  （元件查詢、庫存 API、機械節點寫回、事件派發、Profiler 本身）。

### 4.3 假設（P8 必須驗證）

1. 每棟每 tick 為 O(1)：查表＋加減乘除，無搜尋、排序、LINQ、字串拼接。
2. 無每幀全圖掃描；1 秒 tick（`perf.tickSeconds = 1.0`）、時間差 clamp 在 `[0, 5]` 秒。
3. 材料／道路查詢只在 `condition ≤ 50` 且最多 10 秒一次。
4. 1,000 棟全部同場載入＝上界（實務通常數十棟），p95/p99 必須以 30 秒取樣統計。
5. 離線量測為桌機 .NET 9 JIT；實機是 Unity Mono，兩者 JIT／GC 行為不同，
   離線數字只能當**下界與量級驗證**，不能當 gate。
6. 降頻保命：若實機 p95 >3 ms，記錄並把結算間隔拉長到 2 秒（REQ-SAFE-10），不得改變平衡結果。

## 5. 存檔體積與耗時的推導

```text
§14.7：每棟 pretty ≈ 350 B、compact ≈ 250 B
1,000 棟：350,000 B ≈ 342 KiB（pretty）／250,000 B ≈ 244 KiB（compact）
存檔為 zip 容器，重複鍵名多 → 壓縮比估 1/5
zip 後：~70,000 B ≈ 68 KiB ≤ 400 KiB（§17.3 門檻）→ 餘裕 ×5.9
寫入／載入：各 ≤2 s（1,000 棟）；離線量測 3.05 ms（序列化）／7.30 ms（解析）→ 餘裕 ×656／×274
```

- 門檻口徑（權威）：**zip 後實際檔案 ≤400 KB、寫入 ≤2 s、載入 ≤2 s**；§14.7 的 350 KB 是
  未壓縮估算值，不是門檻。
- 量測方式（P8）：以存檔前後檔案大小差比對 **zip 後實際檔案**；耗時自存檔事件起算至檔案
  落盤（載入則至世界可操作），各量 3 次取中位數並記錄。
- 校驗和、遷移鏈、損壞隔離的效能不在本文件範圍（見 §14.4／§14.5 與 P6 測試）。

## 8. 結論

1. 依 §13.7 拆解，單棟 ≤3 µs、1,000 棟 p95 ≤3 ms／p99 ≤6 ms 的預算是**結構性可達成**的：
   離線代理量測 p95 108.20 µs、p99 167.80 µs，Core 運算只佔預算約 4%。
2. 存檔：§14.7 估算 zip ~68 KiB、實測 synthetic raw 409 KB（序列化 3.05 ms／解析 7.30 ms），
   對 ≤400 KB／≤2 s 門檻有 2～3 個數量級餘裕；記憶體 64 B/棟、1,000 棟 64,000 B 均在上限內。
3. **但效能門檻的權威量測只能在實機做**：離線數字不含 Unity runtime、GC、FPS、UI、動畫與
   真實存檔容器。**1,000 棟 p95/p99、GC、FPS、存檔 zip 大小與耗時、30 日實機模擬全部未做，
   由 P8 人類 gate 補齊**；在那之前，SEE 的效能與平衡不得宣稱「已驗證」。
